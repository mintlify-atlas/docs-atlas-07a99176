CF2CNP includes a hidden easter egg called **YOLO mode**. It generates a single `CiliumNetworkPolicy` that selects every endpoint in a given namespace with an empty `matchLabels` selector and allows all ingress and egress traffic between them — no label matching, no port restrictions. This is intentionally the most permissive policy Cilium can enforce and exists solely to unblock namespaces during active development or testing.

<Warning>
  **YOLO mode is not for production.** The generated policy bypasses all network segmentation within the target namespace. Never apply it to production workloads or any namespace that handles sensitive data.
</Warning>

## CLI usage

Run `cf2cnp yolo ns` to generate the policy for the `default` namespace and print it to stdout:

```bash
cf2cnp yolo ns
```

Target a specific namespace with `--namespace` / `-n`:

```bash
cf2cnp yolo ns --namespace my-dev-namespace
```

| Flag | Short | Default | Description |
|------|-------|---------|-------------|
| `--namespace` | `-n` | `default` | The namespace to generate the permissive policy for |

The command prints a confirmation header followed by the complete YAML:

```
YOLO MODE ACTIVATED!
Generating permissive policy for namespace: my-dev-namespace

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
...
```

Pipe the output directly into kubectl to apply it immediately:

```bash
cf2cnp yolo ns --namespace my-dev-namespace | kubectl apply -f -
```

## API usage

When CF2CNP is running in [server mode](/usage/server-mode), send a `POST /generate` request with the plain-text body `yolo ns` to trigger YOLO mode for the `default` namespace:

```bash
curl -X POST http://localhost:8080/generate \
  -d "yolo ns" \
  -o yolo-policy.yaml
```

To target a specific namespace, append the namespace name after `yolo ns`:

```bash
curl -X POST http://localhost:8080/generate \
  -d "yolo ns my-dev-namespace" \
  -o yolo-policy.yaml
```

The server recognises the `yolo ns` prefix in the request body and routes the request to the YOLO handler automatically — no special headers needed. The same [response modes](/usage/server-mode#response-modes) apply: direct YAML for curl, or JSON with `download_url` when `Accept: application/json` or `X-Grafana-Action` is set.

## Generated policy

The output is a standard `CiliumNetworkPolicy` with empty `matchLabels` everywhere. In Cilium, an empty label selector matches **all** endpoints in the namespace.

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: yolo-allow-all-in-namespace
  namespace: my-dev-namespace
spec:
  description: YOLO! Allow all traffic within the my-dev-namespace namespace.
  endpointSelector:
    matchLabels: {}
  ingress:
    - fromEndpoints:
        - matchLabels: {}
  egress:
    - toEndpoints:
        - matchLabels: {}
```

The output file generated by the server is named `<namespace>-yolo-allow-all-in-namespace.yaml`.

### What the selectors mean

| Field | Value | Effect |
|-------|-------|--------|
| `endpointSelector.matchLabels` | `{}` | Policy applies to every pod in the namespace |
| `ingress[0].fromEndpoints[0].matchLabels` | `{}` | Allow ingress from every pod in the namespace |
| `egress[0].toEndpoints[0].matchLabels` | `{}` | Allow egress to every pod in the namespace |

No `toPorts` rules are specified, so all ports and protocols are permitted.

<Tip>
  YOLO mode is most useful when you are iterating quickly on a new service and want to rule out network policy as a source of connection failures before writing targeted policies. Once your application is working, delete the YOLO policy and replace it with properly scoped rules generated by `cf2cnp generate`.
</Tip>
